# RFC 4287 Atom compatibility audit

The final target is parsing and semantic processing of both RFC 4287 Feed Documents and standalone Entry Documents. This is an implementation audit, not a claim of full conformance. PASS means the narrowly stated requirement has implementation and test evidence; PARTIAL and FAIL identify remaining work.

## API scope and compatibility

The matrix applies to the new parse_atom_document and parse_atom_document_with_base APIs on Git main. They validate the implemented normative rules and return an AtomDocument with distinct FeedDocument and EntryDocument variants. They preserve Atom-specific metadata and an expanded-name XML tree. They are included in the published 0.2.0; the previous 0.1.2 does not include these APIs. A fresh registry project installed and called the exact 0.2.0 module.

The existing parse_atom and unified parse APIs retain their Feed return types and historical common-field normalization behavior. They are not full RFC validators, do not accept an Entry root as a synthetic Feed, and can accept legacy inputs that the document API rejects. All 117 baseline tests remain unchanged; the current suite adds 24 independent Atom conformance cases, two targeted XML Base/date regressions and four internal XML reader cases. See [API compatibility](API_COMPATIBILITY.md). Applications requiring the validation and metadata audited below should migrate to the document API; see README. This deliberate compatibility boundary must not be mistaken for full standards validation across all entry points.

References: [RFC 4287](https://www.rfc-editor.org/rfc/rfc4287), [XML 1.0 Fifth Edition](https://www.w3.org/TR/xml/), [Namespaces in XML 1.0](https://www.w3.org/TR/xml-names/), [XML Base second edition](https://www.w3.org/TR/xmlbase/), [RFC 2045](https://www.rfc-editor.org/rfc/rfc2045), [RFC 2046](https://www.rfc-editor.org/rfc/rfc2046), [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986), [RFC 3987](https://www.rfc-editor.org/rfc/rfc3987), [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339).

## Reproduction and compatibility boundary

Run moon check, moon test, moon test --target js, moon build and moon build --target js with MoonBit >= v0.10.14. The current local result is 147/147 on both default and JS targets: the original 117 baseline tests, 24 independent Atom conformance cases, two targeted XML Base/date regressions, and four internal XML reader cases. Test fixtures and reproduction details are in [fixtures/atom/conformance](../fixtures/atom/conformance/README.md). The Atom example verifies equivalent default/prefixed standalone Entry Documents and prints:

~~~text
Equivalent Entry Documents: PASS
urn:entry:demo
../article
https://example.org/article
~~~

The IANA/IERS leap-transition data is [public domain](https://data.iana.org/time-zones/tzdb/leap-seconds.list). It is data, not a registry/package dependency.

## Remaining work before an unqualified full-conformance claim

1. Complete XML 1.0 DTD behavior: parameter entities, external subsets/entities, markup replacement text and full validity/default handling. External resources must remain opt-in and safely resolved.
2. Add coverage or an explicit policy for media-type-specific parameter equivalence beyond the current known RFC exceptions; arbitrary registry semantics are not queried dynamically.
3. Expand independent normative fixtures, continue the documented manual leap-table review after each IERS bulletin, and decide a versioned migration policy for strict validation on legacy normalization entry points.

The new document API materially closes the standalone Entry, XML Base, metadata-loss and core cardinality gaps. The remaining rows prevent a full RFC 4287 claim. This audit alone does not establish hackathon acceptance.
